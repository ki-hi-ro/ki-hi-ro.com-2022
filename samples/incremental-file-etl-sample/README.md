# Incremental File ETL Sample

## 解決する課題

外部システムから届くCSVを毎回すべて読み込むと、処理済みのデータを繰り返し取り込み、データ量とともに不要な処理時間が増えます。どこまで処理したかも追いにくくなります。

このサンプルは、**ファイル読み込み履歴とinputフォルダの更新日時を比較し、新規・更新ファイルだけをETL処理対象にする**仕組みです。既存ETLの業務ルールを、探索・判定・DBアクセス・取り込みという責務に分けてPython / SQLへ再構成しました。

## Before / After

```text
Before                             After
inputフォルダ                       inputフォルダ
    ↓                                  ↓
全CSVの内容を読み込む                ファイル情報だけ探索
    ↓                                  ↓
毎回すべて処理                      履歴DBと比較
                                       ↓
                                   新規・更新ファイルだけ抽出
                                       ↓
                                   CSVを検証・DBへ取り込み
                                       ↓
                                   成功したファイルの履歴を保存
```

探索では全ファイルのメタデータを確認しますが、CSVの内容は処理対象だけ読み込みます。処理時間の削減率は未計測です。

## 判定例

| ファイル | input | 履歴DB | 判定 |
| --- | --- | --- | --- |
| AAA.csv | 存在 | 同じ更新日時 | SKIP / UNCHANGED |
| BBB.csv | 存在 | inputより古い更新日時 | PROCESS / UPDATED |
| CCC.csv | 存在 | 履歴なし | PROCESS / NEW |

ルールは `inputのmtime_ns > 前回成功時のmtime_ns`、または履歴なし。等しい場合・inputの方が古い場合はスキップします。処理対象一覧を返す関数と、理由つき判定一覧を返す関数を分けています。

## 実行方法

Python 3.12で動作確認。以下の `python3.12` はPython 3.12の実行ファイルを指定してください。SQLiteはPython標準ライブラリを使用します。以下はプロジェクト直下で実行します。

```sh
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

# 元のinputを変更せず、var/demoにコピーと履歴DBを作成
python -m scripts.setup_db

# 判定のみ（CSV取り込み・成功履歴更新はしない）
python -m src.main --input var/demo/input --db var/demo/etl.sqlite3 --dry-run

# 対象ファイルをSQLiteへ取り込み
python -m src.main --input var/demo/input --db var/demo/etl.sqlite3

# 再実行：全件SKIP
python -m src.main --input var/demo/input --db var/demo/etl.sqlite3
```

初回の判定例：

```text
AAA.csv -> SKIP (UNCHANGED)
BBB.csv -> PROCESS (UPDATED)
CCC.csv -> PROCESS (NEW)
Scanned=3 Targets=2 Failed=0
```

実際のログにはUTC更新日時も表示されます。取り込み時は各ファイルの成功件数を表示し、再実行では `Targets=0` になります。更新日時はGitのclone時に変わるため、デモセットアップで比較関係を再現します。AAAとBBBを取り込み済みにし、BBBのinput更新日時だけを後へ進め、CCCは未登録にします。

デモディレクトリが既にあるとセットアップは中止します。再現実験には `python -m scripts.setup_db --demo var/demo2` のように新しい保存先を指定してください。

通常の新規DBからの実行：

```sh
python -m src.main --input input --db var/etl.sqlite3
```

この場合は初回3件すべてがNEWです。`--dry-run`でもDBがなければ空のスキーマを作成します。入力フォルダが空なら正常終了、存在しない場合はエラーです。ファイル単位の失敗後も他ファイルの処理を続け、1件でも失敗すると終了コード1を返します。

## 出力と履歴の設計

SQLiteに以下の架空のテーブルを作成します。

| テーブル | 役割 |
| --- | --- |
| ingestion_history | ファイル名、前回成功時の更新時刻（epoch nanoseconds）、成功時刻（UTC ISO 8601）、行数 |
| sales_records | 元ファイル名、行番号、架空の商品コード、金額 |

CSVはUTF-8、列は `item_code,amount`。商品コードは必須で、文字列として読み込み先頭ゼロを維持します。金額は0以上の整数、SQLite整数範囲内に限定します。ヘッダーだけのCSVは0件として取り込み、空ファイルや不正な列・値は失敗します。

対象ファイルの既存行を削除して新しい行へ置き換えるため、更新のたびに同じファイルの行を追記して重複させません。**データの置き換えと成功履歴更新を同じトランザクションで実行**し、失敗時は両方をロールバックします。次回も失敗ファイルを処理対象にできます。これはファイル単位の最新スナップショットであり、業務キーによる差分更新とは異なります。

値を含むSQLはパラメータ化しています。履歴取得は最大500件ずつ問い合わせ、ファイルごとのSQL往復を減らしています。IN句のプレースホルダー数だけを組み立て、ファイル名自体をSQLへ埋め込みません。

## 既存ロジックからの改善

| 業務ルール・懸念 | Pythonでの表現 |
| --- | --- |
| inputのファイル情報取得 | pathlibによる探索。直下の通常CSVのみ、シンボリックリンクとサブフォルダを除外 |
| 前回読み込み履歴の参照 | HistoryRepositoryにSQLiteアクセスを集約 |
| 新規ファイル判定 | 履歴なしを直接NEWとする。仮の古い日付は使用しない |
| 更新ファイル判定 | 整数のmtime_nsによる厳密な大小比較。秒への丸めをしない |
| 日時の扱い | 比較・保存はepoch nanoseconds。人向け表示はtimezone-awareなUTC日時 |
| 処理対象返却 | processing_targetsが対象だけを返す。classify_filesが理由も返す |
| 失敗時の扱い | 成功時だけ履歴更新。データと履歴を一括commit |

UTCに9時間を加算して日時を作る処理は使用しません。ログのdatetime表示はマイクロ秒精度ですが、判定はファイルシステムから取得した整数のまま行います。

## 運用前に確認すること

- 対象は1つのinputフォルダ・1つのDB・単一ワーカーです。ファイル名を識別キーにしているため、異なるinputフォルダで同じDBを共有しないでください。
- 更新日時だけで判定します。同じ時刻のまま内容を変更した場合や、古い更新日時で再配置した場合は検出しません。ハッシュや配信IDによる検出は要件次第で追加します。
- 実行中はinputを変更しない運用が前提です。前後のmtimeとサイズを検証しますが、あらゆる同時更新を防ぐ仕組みではありません。配信側の一時ファイルからのatomic renameや取り込み領域への移動を検討します。
- 削除されたファイルの履歴・データは自動削除しません。入力の完全性、文字コード、列定義、業務キー、再処理・削除ルール、同時実行制御、大規模データの分割読み込みは本番要件として確認します。
- このサンプルでは対象CSV全体をpandasでメモリに読み込みます。大量ファイルの探索は引き続き必要です。

## 実務経験との関係

**Pentaho ETLからPython ETLへの置き換え業務で扱った処理パターンを、機密情報や実データを含まない形で再構成したサンプルです。** 実際の企業名・業務テーブル名・実データ・既存システムのコードは使用していません。CSVの値とテーブル名はこのサンプル用に作成しました。

背景となる[過去記事「ファイル読み込み履歴テーブルを参照して処理対象ファイルを決定するというロジック」](https://ki-hi-ro.com/【pandas-sql】ファイル読み込み履歴テーブルを参照して/)の判定パターンをもとに、責務の分離、日時精度、失敗時の履歴管理、自動テストを追加しました。本番システム全体やPentahoジョブとの完全互換を示すものではありません。
